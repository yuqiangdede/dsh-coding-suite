# Requirement Clarification

## 目标

把模糊诉求整理成足以进入需求分析的“已确认需求输入”。

## 触发条件

- 只有功能名称或一句“增加/优化/改造”。
- 只有业务方提出的解决方案，没有真实问题。
- 背景、用户、场景、现状、范围、成功标准存在关键缺口。
- 多个解释会直接改变后续方案或工作量。

## 不触发

- 关键信息已经足够，只需做需求分析。
- 已确认方案，只需写 PRD。
- 只是修改文案、字段名或格式。

## 核心规则

1. 不替用户补业务事实。
2. 已有信息不得重复询问。
3. 每轮只问 1–3 个最影响方向的问题。
4. 优先级：核心问题 → 用户与场景 → 现有流程 → 期望结果 → 范围与限制 → 验证标准。
5. 可以给候选项帮助回答，但不能诱导用户确认某个方案。
6. 信息足够后立即停止追问。
7. 明确区分：`已确认事实`、`业务判断`、`待验证假设`、`已有方案`、`待确认`。

## 执行流程

### 1. 提取已知信息

整理：背景、用户、场景、问题、现有流程、目标、范围、限制、依赖、成功标准。

### 2. 判断阻塞缺口

只把会改变以下内容的信息视为阻塞：

- 是否值得做。
- 为谁做。
- 解决什么问题。
- 核心场景。
- 本期边界。
- 核心业务规则。
- 验收方向。

### 3. 分轮澄清

问题必须具体、可回答、能推动决策。禁止一次抛出长问卷。

### 4. 完成条件

满足以下大部分即可结束：

- 背景清楚。
- 目标用户清楚。
- 关键场景清楚。
- 当前问题具体。
- 期望结果清楚。
- 本期范围基本明确。
- 没有会改变方向的重大冲突。

- 核心场景：
