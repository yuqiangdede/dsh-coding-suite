# Project Knowledge Capture

## 目标

让项目做过一次后，后续能够回答“当前规则是什么、为什么这么设计、什么时候变过、哪些经验可复用”。

## 核心原则

1. 资料不等于知识；必须提炼。
2. 以业务对象和未来问题组织，而不是按“PRD/会议纪要/Excel”分类。
3. 事实、规则、决策、变更、数据结论、经验分开表达。
4. 重要决策保留“为什么”和放弃方案原因。
5. 重要变更保留 `旧规则 → 新规则 → 原因 → 影响范围`。
6. 多份材料冲突时先判断时间、正式变更和当前有效性，不能把冲突版本都标记为有效。
7. 材料未提供的确认时间、规则和原因不得虚构。

## 默认知识目录

除非项目已有明确知识库规范，默认按 `references/storage-contract.md` 执行：

- `knowledge/overview.md`
- `knowledge/glossary.md`
- `knowledge/business/`
- `knowledge/decisions/`
- `knowledge/changes/CHANGELOG.md`
- `knowledge/data-insights/`
- `knowledge/lessons/`

## 单条知识建议元数据

尽量记录：

- 项目/业务域
- 业务对象
- 主题
- 类型
- 当前状态：current / historical / deprecated / pending
- 适用范围
- 来源
- 确认时间（材料存在时）
- 变更关系

## 执行流程

1. 读取项目材料并建立来源清单。
2. 提取事实、规则、决策、变更、结论和经验。
3. 去重并过滤临时讨论/无结论信息。
4. 补充必要上下文。
5. 处理冲突和版本关系。
6. 按业务对象写入固定目录。
7. 提炼跨项目经验；满足稳定性门槛时再建议 Checklist/SOP/Skill。
8. 输出“当前有效规则”和“待确认知识”清单。

## 输出

- 项目知识总览
- 当前有效业务规则
- 产品/技术决策记录
- 需求变更历史
- 数据结论
- 项目经验
- 待确认/冲突项
- 新增/更新的知识文件清单
- 可进一步固化的通用资产


## DSH 接入约定（本地适配）

执行前读取 [产品需求技能接入规则](../_shared/PRODUCT_DEVELOPMENT.md)，遵循目标项目的知识权威、阶段范围、版本关联与结果标记约定。已有明确决定直接复用。
