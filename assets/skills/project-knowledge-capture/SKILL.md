# Project Knowledge Capture

## 目标

让项目做过一次后，后续能够回答“当前规则是什么、为什么这么设计、什么时候变过、哪些经验可复用”。

## 核心原则

1. 资料不等于知识，必须先提炼并核对来源。
2. 以业务对象和未来问题组织，而不是按 PRD/会议纪要/Excel 分类。
3. 事实、规则、决策、变更、数据结论和经验分开表达。
4. 重要决策保留选择理由与放弃方案；重要变更保留旧规则、新规则、原因及影响。
5. 多份材料冲突时检查时间、正式变更、适用范围及当前状态，不能同时标记冲突规则为有效。
6. 材料未提供的确认时间、规则与原因不得虚构。
7. **复用项目原有权威文档，不创建第二套 knowledge/ 或 Pocket 副本。**

## 知识存放位置

执行前先读取 [项目文档单一权威位置协议](../_shared/DOCUMENT_AUTHORITY.md) 和 [知识位置映射](references/storage-contract.md)。

- 读取目标项目 Agent 指令、现有需求/设计/ADR/运维文件和知识索引；对每个业务对象先定位当前有效的权威文档。
- 已有文档优先原位置增量更新；缺少该主题且现有分类目录适用时沿用原目录。
- 只有没有适用现有位置时，才按需写入 `docs/pocket/`；Pocket 索引可指向任何被确认的项目内权威文件，不复制正文。
- **禁止再默认生成 `knowledge/` 目录**；已有 `knowledge/` 是被项目认可的权威时保留并复用，而不是强行迁移。
- 已有索引优先更新；不存在时可建立最小 Pocket 索引，但不得把索引写成新的业务正文。

## 单条知识建议元数据

- 项目/业务域、业务对象、主题及类型
- 当前状态：current / historical / deprecated / pending
- 适用范围、权威来源路径、可追溯证据
- 确认时间（材料明确存在时）与关联变更

## 执行流程

1. 读取现有项目规范、索引、材料及 Git 工作区状态，建立来源清单与每个主题的目标权威路径表。
2. 提取事实、规则、决策、变更、数据结论和经验，去重并排除无结论讨论。
3. 核对版本与冲突；标出没有充分证据的部分，不自动改变已确认规则。
4. 对每个目标文件形成差异预览，显示新增/更新、相关索引、引用和影响范围。**取得明确确认后才写入正式知识**；不自动提交或推送。
5. 在确定的权威文件做最小增量更新；仅对完全缺失的主题惰性新增文档，不建立空目录或第二个权威版本。
6. 更新现有知识索引（如有）和引用；对过时版本保留状态及后继指针。
7. 按需提炼跨项目经验；满足稳定性门槛时再建议 Checklist / SOP / Skill。
8. 检查变更文件、相对链接、现行状态和 Git diff；输出未解决冲突与检查边界。

## 输出

- 每个主题的现行权威文件和状态
- 当前有效业务规则与产品/技术决策
- 需求变更与数据结论、复用经验
- 待确认/冲突项
- 差异预览、已确认写入的文件、索引修改和实际校验结果

## DSH 接入约定（本地适配）

执行前读取 [产品需求技能接入规则](../_shared/PRODUCT_DEVELOPMENT.md)，遵循目标项目的知识权威、阶段范围、版本关联与结果标记约定。已有明确决定直接复用。
