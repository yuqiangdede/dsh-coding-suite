# 质量验证、反向审查与长期治理

阶段 Gate、P7 和 P8 使用。测试证据记录命令、环境、数据、版本、时间、退出码、结果与覆盖范围。

## P7：系统级验收、性能优化与故障验证
必须验证重构后的系统能否达到预期。

### 正确性

- 核心功能正常。
- 已确认的业务规则保持一致。
- 关键接口契约正确。
- 数据一致性符合要求。
- 前端主要业务流程正常。
- 权限与安全边界正确。

### 性能
性能优化必须基于实测。
至少考虑：

- P50、P95、P99 延迟。
- 吞吐量。
- CPU 和内存。
- JVM 堆、GC 和线程。
- 数据库慢 SQL。
- 查询执行计划。
- N+1 查询。
- 连接池。
- 缓存命中和失效。
- 网络请求次数。
- 前端包体积。
- 页面加载性能。
- Vue 组件重复渲染。
- 长列表性能。
- 内存泄漏。
- 事件监听与定时器释放。
Java、数据库和 Vue 的优化不能只依赖经验判断。
应先测量瓶颈，再针对热点优化，然后重新测量。
负载数据、硬件条件、并发数、样本量和统计方法必须尽可能保持可比。
不得伪造性能提升百分比。

### 可观测性
建立能快速定位问题的机制。
至少涵盖：

- 结构化日志。
- traceId / requestId。
- 错误码。
- 异常根因。
- 跨模块调用链。
- SQL 耗时。
- 外部接口耗时。
- 关键业务指标。
- 慢请求记录。
- 重要失败告警。
- 必要的健康检查。
- 故障恢复和排查手册。
可考虑 OpenTelemetry，但必须根据规模评估复杂度和成本。
日志不得泄露密码、访问令牌、敏感身份信息及完整业务敏感数据。

### 架构质量
验证：

- 是否出现新的循环依赖。
- 是否越过模块边界。
- 是否出现巨型 Service。
- 是否违反层次依赖。
- 是否产生新的重复代码。
- 是否存在不必要的抽象。
- 重要逻辑是否具备可测试性。
- 新模块是否符合已批准的架构设计。

## P8：旧实现退役与架构治理
检查：

- 所有计划保留的能力是否已迁移。
- 不再使用的旧代码是否可以安全删除。
- 旧数据库字段和表是否仍被引用。
- 旧 API 是否仍有调用方。
- 旧配置和依赖是否仍然必要。
- 历史兼容适配器是否已经可以移除。
- 运维文档是否更新。
- 故障处理流程是否经过验证。
- 架构规则是否接入自动化检查。
旧代码删除必须基于引用、运行行为和迁移验收证据。
不能因为静态搜索没有发现引用，就直接认定某段代码没有用途。
应持续维护架构决策记录和技术债清单。

# 九、完整的模块验收标准
任何模块不能因为“编译通过”就判定重构完成。
必须检查以下方面：

### A. 业务正确性
功能符合已确认的行为契约。

### B. 架构合理性
模块边界明确，没有违反依赖规则。

### C. 代码质量
核心代码职责清晰、易阅读、易修改、不过度设计。

### D. 测试质量
具有与风险相适应的自动化测试及明确的执行结果。

### E. 数据正确性
数据访问、事务和并发行为符合要求。

### F. 异常与排障能力
发生错误可以识别原因和调用位置。

### G. 性能
达到预先确认的性能基准或性能预算。

### H. 安全性
权限、输入验证、敏感数据和外部调用经过验证。

### I. 集成兼容性
前后端和外部系统契约正确。

### J. 可回滚性
涉及切换时有适用的回滚策略，并验证其可行性。
不适用的项目可以标记 N/A 并说明原因。
未验证项目不得标记为通过。
发现重大缺陷时，模块状态应为验收失败或阻断。

# 十、独立反向审查机制
在每次重大架构设计、核心模块迁移和系统级验收之后执行独立审查。
审查时不应只是重复之前的设计理由。
应主动寻找：

- 是否遗漏旧业务规则。
- 是否制造新的模块耦合。
- 是否过度设计。
- 是否存在隐藏的共享数据。
- 是否存在不可控的事务边界。
- 是否有并发或资源泄漏问题。
- 是否存在数据迁移风险。
- 是否破坏前后端契约。
- 是否缺少失败场景测试。
- 是否使排障更加困难。
- 是否引入不必要的性能成本。
- 是否存在更简单的实现方式。
审查结果按：

- P0：必须立即解决的严重问题。
- P1：当前阶段必须解决的重要问题。
- P2：建议改进。
- P3：可选优化。
每项发现提供代码证据、影响范围、复现或验证方法，以及建议方案。
不能用缺乏证据的主观判断直接判定代码有严重问题。
对于未解决的 P0 问题，不得通过验收。
对未解决且影响当前交付的 P1 问题，应阻止验收或由用户明确接受风险。

## 审查执行

重大架构、核心模块迁移和系统级验收之后执行独立反向审查。有可用且获授权的独立审查 Agent 时可采用独立上下文，否则单独进行第二轮反向审查，重新从源码、契约、数据所有权和失败路径取证。不得把自述实现理由当作审查证据。审查严重度 P0–P3 与流程阶段 P0–P8 分别记录。

未解决的严重度 P0 阻止验收；影响当前交付的 P1 阻止验收，除非用户明确接受可接受的风险。记录用户接受的范围、理由、责任人与补救条件，不能豁免 P0。

## 长期治理

将可执行的边界、循环依赖、API 兼容、测试和性能预算接入现有 CI。保存 ADR、技术债、废弃接口调用证据及复查条件。P8 的静态零引用只是线索，还须核对反射、配置注册、动态路由、定时任务、外部调用方和真实运行窗口。确认迁移验收、恢复手册与退役授权后再移除旧代码/表/适配器。
