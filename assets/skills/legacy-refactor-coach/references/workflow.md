# 九阶段状态机

选择重新实现时，按 reimplementation.md 的 R0–R4 引导并映射本状态机；新旧行为对比、兼容迁移、切换和旧系统退役仅在实际适用时执行，不适用项记录理由。已确认目标契约是验收依据，不以旧实现行为作为默认标准。

## 状态与转换

每个阶段和模块各自记录 `未开始 / 执行中 / 等待决策 / 验证失败 / 已通过 / 已阻断 / 暂时跳过`。首次进入为执行中。缺少必要批准进入等待决策；实际检查失败进入验证失败；环境或依赖使任务无法进行时进入已阻断，并记录恢复条件。

只有当前范围全部必需验收项具有有效证据、严重问题关闭且必要决定已记录，才能进入已通过。已通过后才进入下一阶段。用户要求跳阶段时检查缺失证据，补齐当前能力所需最小基线；局部跳过只记录未覆盖范围和理由，不能冒充已通过。核心安全、行为保护和当前交付门禁不得跳过。

证据随源码、契约或运行环境变化失效时，相关阶段回到执行中复核，下游依赖同步标待复核；保留历史结果。一般分析与低风险步骤无需逐项确认，重大操作遵循入口的授权范围。

## P0 项目初始化与重构基线

- 目标为识别真实项目、授权范围、运行限制和资料路由。
- 前置条件为可访问工程；路径未知时只询问无法自行定位的关键信息。
- 读取 Git 状态、构建/锁文件、部署配置、项目规则和现有文档；按 discovery.md 收集 Java/Spring/Vue/数据库/中间件等版本及构建启动方式。
- 操作为区分证据类别，识别原位或新工程方案、生产兼容和不可中断能力，核对 dirty diff；非关键且可撤销项采用明确标注的默认值。
- 交付为项目画像、状态文件、路径映射、基线与未知项。
- 验收为路径、工作模式、范围、实际栈、可执行验证方式和必要决策都有证据或明确未知标签。
- 阻断为工程无法定位、权威路径冲突或影响当前任务的关键业务决策缺失。缺少运行条件不能伪造运行基线。
- 下一阶段条件为 P0 通过，P1 的静态审计具备访问与范围依据。

## P1 历史工程全面审计

- 目标为还原业务行为、依赖、数据和风险。
- 前置条件为 P0 通过或当前功能等价的局部基线已核实。
- 读取真实入口、Controller/Service/Mapper、Vue 页面/路由/状态/API、SQL/迁移、测试与外部依赖；使用 discovery.md 和相关技术专项。
- 操作为追踪关键业务调用链、数据读写与隐含规则，执行适用构建/测试并保留失败证据。
- 交付为功能地图、后端依赖图、前端组件关系、数据所有权、外部依赖、技术债、风险、构建测试基线和未知项。
- 验收为范围内主要入口到数据路径可追溯，结论有源码位置与版本，覆盖边界明确。
- 阻断为关键行为或数据路径无法确认；环境故障按影响划分，允许继续可独立的源码分析。
- 下一阶段条件为 P1 通过，能力取舍所需证据可供 P2 决策。

## P2 功能筛选与业务边界

- 目标为决定保留能力及数据所有者，避免复制旧包边界。
- 前置条件为当前能力审计证据有效。
- 读取功能地图、业务契约、调用方、缺陷与用户决策，使用 architecture.md。
- 操作为逐项标记复用、重实现、局部优化、合并、暂缓、删除或待决策；比较价值、成本、风险、耦合与解锁作用；反方审查划界。若目标为重新实现，先展示完整范围的功能清单并由用户选择保留项；所有保留项均从零实现，不沿用旧代码或实现逻辑，未决项不擅自舍弃。
- 交付为能力清单、统一语言、边界与上下文关系、共享数据处理方案、迁移优先级。
- 验收为范围内每项能力有处置依据与所有者，当前迁移所需业务选择已确认，未决能力保持保留状态。
- 阻断为共享写入责任或关键功能去留未决定。
- 下一阶段条件为 P2 通过，P3 有明确范围与边界输入。

## P3 目标架构设计

- 目标为建立适合规模且可检验的架构和契约。
- 前置条件为当前范围 P2 决策明确。
- 读取能力清单、现有架构/ADR、版本与部署约束，使用 architecture.md。
- 操作为评估模块化单体、分层、必要适配器，定义模块公开接口、数据所有权、事务和前后端契约；比较关键候选方案并反向审查。
- 交付为架构边界、依赖规则、API 契约、适用 ADR、质量预算和迁移接口。
- 验收为依赖方向、权限、兼容、事务及故障归宿可检查，关键设计已确认，审查阻断项关闭。
- 阻断为循环依赖无法解释、数据责任冲突、不可行兼容或重大设计待决。
- 下一阶段条件为 P3 通过，P4 可以据此建设最小工程与验证约束。

## P4 工程骨架与质量基础设施

- 目标为迁移前建立可重复构建与验证环境。
- 前置条件为架构和当前实施范围已确认，执行模式获得授权。
- 读取构建配置、测试、CI、异常/日志/配置实现与两端技术专项；工具均为按版本适用的候选。
- 操作为建设最小骨架、后端/前端基础测试、契约与架构检查、统一异常、结构化日志和请求关联标识、密钥配置管理及最小 CI。
- 交付为构建测试命令、实际结果、质量检查配置、开发启动与排障工作稿，正式文档沿用批准流程。
- 验收为构建与当前范围所需检查实际可执行，失败有真实恢复记录，新增依赖有用途且兼容。
- 阻断为当前范围无法构建/测试或依赖环境缺失；先最小恢复，不能标记为通过。
- 下一阶段条件为 P4 通过，试点行为能够先受测试保护。

## P5 首个业务模块试点

- 目标为完成一个真实能力的完整迁移闭环。
- 前置条件为 P0–P4 当前范围通过，已有明确实施计划。
- 读取旧实现、调用方、数据与隐含规则、已确认契约，使用 migration.md 和 verification.md。
- 操作为测试保护、模块接口与实现、基础设施适配、前后端集成、契约验证、架构检查、异常日志、性能测量、反向审查及适用的切换回滚验证。重新实现时依据确认的业务规则编写测试，旧行为只作证据而不自动继承；仅在确有兼容要求时对比旧行为。
- 交付为唯一模块 ID、代码、测试、审查、兼容方案、切换及回滚证据、可复用模板。
- 验收为 verification.md 的 A–J 均通过或合理 N/A，必要切换在授权范围完成且被验证。
- 阻断为行为回归、数据错误、关键证据缺失或审查 P0/P1 未关闭且无适用风险接受。
- 下一阶段条件为 P5 通过后才可将经验推广到 P6，不能复制未验收模式。

## P6 按模块持续迁移

- 目标为逐个独立能力替换旧实现。
- 前置条件为试点验收通过，当前单元具备唯一 ID、依赖与批准计划。
- 读取当前模块审计、公共契约及共享代码调用方，使用 migration.md。
- 操作为审计 → 设计 → 测试保护 → 实现 → 集成 → 复核 → 验收 → 切换；每次一个单元，分析公共契约影响和新旧并存。
- 交付为模块迁移记录、实现、测试、数据校验、切换与回滚状态和更新后的路线图。
- 验收为每个迁移单元通过 A–J，数据写入所有者、幂等、重试、缓存/MQ/定时任务与滚动发布兼容有证据。
- 阻断为部分失败不一致、不可回滚、无授权副作用或当前 Gate 失败。
- 下一阶段条件为当前单元通过才推进下一单元；计划保留的本批能力迁移完毕才进入 P7。

## P7 系统验收、性能与故障验证

- 目标为验证整体业务、契约、性能、权限及恢复能力。
- 前置条件为本批 P6 单元通过且集成环境、负载与预算明确。
- 读取全部本批验收结果、关键链路、性能基线与故障手册，使用 verification.md。
- 操作为端到端业务/数据/安全验证，可比负载性能测量，定位热点后复测，故障注入与恢复验证在获授权的隔离环境完成，执行反向审查。
- 交付为系统验收、可观测性、故障恢复和可比性能报告，记录未覆盖项。
- 验收为业务和前后端流程正确，性能达到预定预算，异常可定位且恢复路径实测，严重审查问题已处理。
- 阻断为核心规则回归、数据/权限错误、预算不达标或恢复未验证。
- 下一阶段条件为 P7 通过且退役范围明确，才进入 P8。

## P8 旧实现退役与长期治理

- 目标为有证据地退役旧能力并持续防止架构退化。
- 前置条件为 P7 通过，兼容窗口、真实调用证据和退役授权已核实。
- 读取旧 API/表/配置/适配器引用、运行窗口、外部调用方、ADR 与技术债，使用 verification.md。
- 操作为核对静态与动态使用、备份恢复、兼容窗口，按授权清理旧实现；将依赖规则、测试与预算接入 CI，维护运维及排障资料。
- 交付为退役清单、证据、实际清理结果、治理规则与后续责任记录。
- 验收为计划保留能力均有有效验收，退役对象无存续依赖，恢复资料和自动化规则有效。
- 阻断为未知调用方、仅有静态零引用、无可靠恢复路径或删除授权缺失。
- 后续条件为退役检查通过后标记本批完成，剩余暂缓能力另立计划，按既有 CI 与复查周期持续治理。
