# 试点与渐进迁移

P5、P6 使用。先满足 workflow.md 的当前范围门禁。选择重新实现时，以确认保留的功能及业务契约为依据从零实现，不复制或沿用旧实现逻辑；下述旧行为对比、兼容与切换步骤仅在实际需要时适用，记录不适用原因。

## P5：首个业务模块试点重构
优先挑选：

- 边界相对清晰。
- 功能价值明确。
- 可验证输入输出。
- 数据影响较小。
- 对其他模块依赖较少。
- 可以独立交付。
试点不能只做目录调整。
必须完成一个真实业务能力从旧实现到新架构的完整闭环。
包括：
1. 分析旧代码。
2. 提取业务行为。
3. 识别隐含规则。
4. 建立特征测试。
5. 设计模块接口。
6. 设计新代码结构。
7. 实现业务逻辑。
8. 实现必要的基础设施适配。
9. 编写单元测试和集成测试。
10. 验证前后端契约。
11. 对比新旧行为。
12. 执行架构检查。
13. 验证异常与日志。
14. 对比关键性能指标。
15. 生成审查报告。
16. 制定切换及回滚方案。
17. 在授权范围内完成切换。
18. 验收后总结可复用模块模板。
试点没有通过验收，不得直接复制问题模式到其他模块。

## P6：按模块持续迁移
必须采用按业务能力推进的工作循环。
对每个模块执行：

**审计 → 设计 → 测试保护 → 实现 → 集成 → 复核 → 验收 → 切换。**
建议每次只推进一个可独立验证的功能单元。
每个功能单元必须具备唯一编号。
禁止单次任务跨多个无关业务模块进行大规模改动。
如果涉及共享代码或公共契约修改，必须分析潜在影响。

### 迁移保护
需要特别处理：

- 新旧接口兼容。
- 数据库结构变更。
- 数据迁移。
- 历史数据转换。
- 事务一致性。
- 并发和锁。
- 缓存一致性。
- 消息重复消费。
- 定时任务重复执行。
- 外部接口副作用。
- 资源释放。
- 权限变化。
对于无副作用的计算功能，可以通过新旧输出对比验证。
对于查询，可以在安全条件下采用影子请求或流量分流。
对于数据库写入、发送消息、设备操作以及其他有副作用的操作，不得为了对比而无条件执行两次。
涉及数据库结构变化，应考虑 Expand-Migrate-Contract 之类的兼容迁移策略。
必须明确数据写入所有者。
如果多个版本共存，应验证滚动发布和回滚期间的兼容性。

### 代码质量要求

- 方法职责明确。
- 类职责明确。
- 命名能够表达业务意图。
- 避免魔法值。
- 避免复制粘贴式实现。
- 不进行无价值的过度抽象。
- 不随意制造继承层级。
- 优先组合而非复杂继承。
- 避免无边界的全局工具类。
- 业务规则集中到正确模块。
- 异常必须有清晰语义。
- 资源必须正确关闭和释放。
- 对复杂逻辑使用有业务价值的注释。
- 不允许依靠大量注释掩盖设计混乱。
以行为正确、职责清楚和可维护性为目标，而不是追求最少代码行数。

## 切换与回滚记录

为每个单元指定唯一 ID、业务所有者、数据写入所有者、旧入口、新入口、路由开关、兼容窗口、特征/契约测试、切换前置条件和回滚触发阈值。先验证小范围闭环，再扩展到下一单元。

数据库采用适用的 Expand-Migrate-Contract。扩展保持旧版本可读写，回填记录游标、校验和、幂等键与失败重试，迁移后核对数量、关键值及业务不变量。双版本共存验证滚动发布和回滚，明确切回旧代码后新增数据如何处理，不能将代码回滚视为数据自动恢复。收缩或删除前验证全部调用方和备份恢复证据，并核实明确授权。

只对无副作用计算做双实现对比，查询影子请求须评估负载与数据暴露。写数据库、发消息、设备操作、定时任务和外部调用禁止盲目双执行。明确分流期间任务唯一执行者及消息消费去重。迁移前验证超时、部分失败、重试、补偿、权限及资源释放。
