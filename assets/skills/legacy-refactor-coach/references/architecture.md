# 能力筛选与目标架构

P2、P3 使用。按业务能力和数据所有权划界。

## P2：功能筛选与边界划分
这一阶段不能直接按照旧包结构划分新模块。
应从实际业务能力出发。
建立功能目录，逐项标记：

- 保留并复用。
- 保留但重新实现。
- 保留并进行局部优化。
- 合并重复能力。
- 暂缓迁移。
- 明确删除。
- 待用户决策。
每个能力至少记录：

- 功能 ID 和名称。
- 业务价值。
- 入口和调用路径。
- 输入输出。
- 关键业务规则。
- 使用的数据。
- 与其他能力的依赖。
- 当前缺陷。
- 兼容要求。
- 推荐处理方式。
- 迁移复杂度。
- 测试难度。
- 风险等级。
接下来采用 DDD 战略设计思路划分业务模块。
特别分析：

- 模块职责是否独立。
- 是否存在多个模块修改相同业务数据。
- 是否存在不必要的双向依赖。
- 哪些功能应当聚合。
- 哪些功能应当拆分。
- 哪些模块需要公开服务接口。
- 哪些技术能力应属于基础设施而不是业务模块。
对模块划分进行反方审查。
不要把旧系统的错误边界带到新系统。
用户尚未决定的功能，不能擅自删除。

## P3：目标架构设计
给出适合当前项目规模的目标架构，而不是照搬通用架构模板。
默认优先评估：

**模块化单体 + 按业务组织模块 + 清晰分层 + 必要的端口适配器。**

### 后端建议分层
每个需要明确分层的业务模块可包含：

- api：接口入口、请求和响应 DTO。
- application：用例编排、事务协调、权限及流程控制。
- domain：业务模型、规则和不变量。
- infrastructure：持久化和外部技术适配。
不要求简单业务模块机械创建所有层次。
必须定义依赖规则：

- 领域层不依赖 Web 框架、ORM 实现或外部 SDK。
- 基础设施实现依赖业务侧定义的接口。
- 应用层主要负责协调，不堆积复杂业务规则。
- 控制器不直接编写复杂业务逻辑。
- 不允许绕过模块公开接口直接操作其他模块内部实现。
- 不允许随意跨模块访问和修改他人管理的数据表。
- 避免循环依赖和不必要的双向关联。
- shared 模块只包含职责稳定、经过验证可复用的能力。
如需异步事件，应明确最终一致性、重试、幂等和故障处理要求。
不得为了所谓解耦而把所有调用转换成消息队列。

### 前端建议架构
根据现有 Vue 版本确定方案。
优先采用按业务功能划分目录，例如：

- app：应用初始化。
- router：路由。
- features：业务功能模块。
- shared/components：稳定通用组件。
- shared/api：通用 HTTP 能力。
- shared/utils：真正通用的工具。
- layouts：页面布局。
- styles：全局样式与设计规范。
每个业务功能按需包含：

- pages
- components
- api
- composables
- stores
- types
- tests
Vue 2、Vue 3 采用各自兼容的实现方式。
禁止未评估就强制升级 Vue、Spring Boot、Java、UI 库及其他基础依赖。

### 前后端协作
明确：

- API 契约。
- DTO 与数据模型边界。
- 分页、筛选、排序规则。
- 错误码与错误提示。
- 时间、时区及数据格式。
- 身份认证和授权规则。
- 版本兼容和废弃策略。
- 文件上传下载规范。
- 长任务和异步请求规范。
权限判断以后端为最终安全边界，前端权限只负责交互控制。

### 架构决策
对于存在多个合理方案的关键问题，应提供：

- 方案 A。
- 方案 B。
- 优缺点。
- 对当前工程的适用性。
- 成本及风险。
- 推荐选择。
- 决策依据。
重大架构决策应记录 ADR（Architecture Decision Record）。
禁止没有依据地引入微服务、CQRS、Event Sourcing、复杂事件总线或大量中间抽象。

## 方法选择

按情境组合 Strangler Fig 渐进替换、DDD 战略边界、Clean Architecture 依赖方向、Hexagonal 端口适配器、模块化单体、Characterization Testing、Branch by Abstraction、演进式架构与 Anti-Corruption Layer。存在真实依赖隔离需求时再增加抽象，简单业务裁剪层次。重大决策比较两个真实可行方案，记录依据、成本、风险、批准范围与复核条件，ADR 复用项目正式位置。

# 八、重构优先级和任务选择机制
不能完全按旧目录顺序重构。
应结合：

- 业务价值。
- 保留必要性。
- 修改成本。
- 技术复杂度。
- 风险。
- 外部依赖。
- 测试难度。
- 模块耦合度。
- 对其他模块的解锁作用。
建立可解释的优先级排序。
优先选择收益明确、风险可控、容易建立质量基准的模块。
对于高风险但又是关键依赖的模块，可以先进行隔离和测试保护，再安排迁移。
不要为了获得简单的高分而长期回避关键业务模块。
对每个候选任务给出推荐理由。
