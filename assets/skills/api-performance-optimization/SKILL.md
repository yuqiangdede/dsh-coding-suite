# API Performance Optimization｜单接口性能优化

## 定位接口

先读目标项目 Agent 指令、文档布局、Pocket 或现有知识索引及接口定义，识别语言、框架、数据库和缓存。根据用户描述、HTTP 方法和 URL、Controller、方法名或代码上下文唯一定位接口。仍无法唯一定位时，只询问目标接口。范围限于该请求实际经过的代码和必要依赖。

## 追踪调用链和瓶颈

从入口顺实际执行路径追踪 Service、DAO/Mapper、数据库、缓存、外部服务及结果处理。记录关键方法、文件与行号、顺序和调用关系、SQL 和外部请求、循环与重复调用、同步/异步/并行关系及可取得的耗时和次数。

检查慢 SQL、索引、扫描行数、N+1、重复查询、串行或重复外部请求及超时、缓存失效或未复用、重复计算、大结果集、对象转换和序列化、锁等待、线程池排队、连接池等待及重复鉴权或业务处理。按证据支持的耗时、调用次数及改善空间排序。每项标注「已确认」（有指标、执行计划或可复现证据）、「高概率」（有明确源码证据，尚未运行验证）或「待验证」（只有假设）。

## 建立基线

优先复用项目现有诊断 Skill、日志、链路追踪、慢查询记录、SQL 执行计划及测试工具。在允许的开发或测试环境中固定请求参数、数据量和并发条件，分别记录首次和预热后请求，报告样本数、P50、P95。必要时添加最小范围的计时，并按项目约定清理临时探针。并行步骤以实际关键路径计时，禁止直接相加。无运行条件时继续静态分析，耗时和次数缺失时标记「未测量」，禁止编造。

## 优化与回归

用户要求实施时，可直接应用并验证低风险、小范围、收益明确的修改。优先消除重复 SQL、外部调用和计算，适当批量化或并行，复用现有缓存及查询机制。保持返回字段、排序、分页、异常处理、权限和事务语义。涉及 DDL、缓存一致性变更、事务语义变更、生产配置、生产压测或不可逆操作，先给方案并等待明确授权。禁止自动连接或压测生产环境、修改线上配置或提交代码。

运行可用的编译、单元测试和目标接口回归。在等效条件下比较优化前后响应耗时、SQL 次数、外部调用次数及结果一致性。验证失败时检查并按需撤回本次修改，保护用户已有变更。缺少稳定实测条件时，如实列出限制，不宣称性能提升。

## 输出

1. 接口信息：地址、入口方法、目标问题。
2. 调用链与耗时：表格列出步骤、源码位置、实测耗时和调用次数，缺失填「未测量」。
3. 主要瓶颈：按收益排序，列出证据等级、根因和影响。
4. 优化结果：修改文件、修改方式、原因和可能的副作用。
5. 验证结论：前后指标、功能回归、未验证项目及剩余风险。

报告和采集内容必须脱敏，不输出敏感参数、Token 或凭据。文件型分析与验证产物放到项目登记的任务工作区，正式资料变更先展示差异并确认。
