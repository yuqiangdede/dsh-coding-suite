# Version Retrospective

## 目标

把一次版本经历转化成下一次可执行的改进，而不是只总结“发生了什么”。

## 输入

可使用：原始需求、需求分析、方案、PRD、评审记录、计划、变更、技术方案、Bug、测试、上线记录、数据、用户/业务反馈、关键决策。

材料不足时区分：`已确认事实`、`合理判断`、`待确认`。

## 分析框架

1. **目标复盘**：原目标、成功标准、基线、实际结果。
2. **结果复盘**：达成/部分达成/未达成/暂时无法判断。
3. **过程复盘**：需求 → 方案 → 评审 → 开发 → 测试 → 上线 → 数据观察。
4. **根因分析**：继续追问到可改变的流程、规则、工具或决策机制，不把“沟通不到位”当最终根因。
5. **有效做法**：识别应继续保留的方法。
6. **系统性问题**：判断是否会跨项目重复。
7. **行动固化**：Continue / Stop / Start + Owner + 触发时机 + 验收方式。

## Skill 化门槛

复盘结论默认优先沉淀为 Checklist、SOP、模板或规则。

只有满足以下任一条件，才建议创建/修改 Skill：

- 同类问题或有效做法已在多个项目/版本重复出现；
- 明显属于跨项目、长期稳定的工作流；
- 用户明确要求 Skill 化。

单次偶发故障、人员临时变化、一次性外部事件不得直接催生新 Skill。

## 改进动作标准

每条动作尽量包含：

- 改什么。
- 在哪个阶段执行。
- 谁负责。
- 什么情况下触发。
- 产出什么。
- 如何证明已经执行。

禁止只写“加强沟通、提前规划、提高质量”。

## 输出

- 版本目标与结果对照
- 关键事件时间线
- 做得好的地方
- 问题清单
- 根因分类
- 偶发 vs 系统性判断
- Continue / Stop / Start
- 改进动作表
- 建议沉淀资产：Checklist / SOP / 模板 / 规则 / Skill（满足门槛时）
