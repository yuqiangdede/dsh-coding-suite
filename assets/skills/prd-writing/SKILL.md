# PRD Writing

## 目标

把已确认方案写成：可开发、可测试、可验收、可追溯的产品需求文档。

## 前置条件

应基本明确：背景、用户、场景、方案方向、范围、核心对象、主流程、关键状态和权限框架。

若核心方案尚未确认，转 `solution-design`；若问题本身仍模糊，转需求澄清/分析。

## 职责边界

### 本 Skill 负责

- 新写 PRD。
- 根据确认结果补全/重构 PRD。
- 把流程、规则、原型说明转成研发规格。
- 细化字段、触发、状态、权限、异常、通知和验收标准。

### 本 Skill 不负责

- 不做最终 GO/NO-GO 评审。
- 不输出 S0/S1/S2/S3 风险评级作为正式评审结论。
- 不在写作过程中重新决定核心方案。

## 核心规则

1. 未确认业务事实不得写成确定规则。
2. 核心规则按 `条件 → 动作 → 结果` 描述。
3. 先对象/流程/规则，再页面细节。
4. 正常路径与异常路径必须同时说明。
5. 权限区分页面可见、数据可见和操作权限。
6. 状态必须写进入条件、允许操作、退出条件和终态。
7. 验收标准优先使用 Given / When / Then。
8. 明确本期范围、非目标、延期项和依赖。

## 推荐结构

1. 文档信息与变更记录
2. 背景与目标
3. 用户与角色
4. 场景与范围
5. 非目标
6. 核心业务对象
7. 业务流程
8. 状态流转
9. 角色与权限
10. 功能需求
11. 字段与数据规则
12. 异常与边界
13. 通知/任务/审计（如适用）
14. 页面与交互要求
15. 数据指标/埋点（如适用）
16. 验收标准
17. 风险与依赖
18. 待确认事项

## 输出标记

无法确定但不阻塞主体时，使用：

- `待确认`
- `建议方案`
- `默认假设`
- `技术评估后确认`

完成后只说明“PRD 草案/确认版已形成”，不要自行宣告“可直接进入研发”。是否放行由 `requirement-review` 决定。

详细模板可放在 `references/prd-template.md`，主 Skill 保持精简。


## DSH 接入约定（本地适配）
