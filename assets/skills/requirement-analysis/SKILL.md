# Requirement Analysis

## 目标

回答“为什么做、为谁做、真正问题是什么、本期该解决到哪里、如何验证”。

## 前置条件

至少基本明确：需求背景、主要角色、关键场景、当前问题、期望改善方向。否则回到 `requirement-clarification`。

## 不负责

- 不直接选择最终产品方案。
- 不做详细页面设计。
- 不编写完整 PRD。
- 不把业务方提出的功能当成已经证明的需求。

## 核心原则

1. 先问题，后方案。
2. 区分事实、判断、假设和已有方案。
3. 问题必须表达为：`角色 + 场景 + 任务 + 原因/限制 + 问题表现 + 影响`。
4. 从流程和场景寻找根因，不把表面现象直接当根因。
5. 范围围绕核心问题，不因“相关”自动扩张。
6. 多个合理方向只列为候选，不替业务做最终决策。

## 分析维度

- 背景与触发原因。
- 用户/角色及目标冲突。
- 核心场景。
- As-Is 流程。
- 问题表现与影响。
- 根因与证据。
- 核心业务对象。
- 已知业务规则。
- 本期范围与非目标。
- 风险、依赖和约束。
- 验证指标与基线。

## 执行流程

1. 归类输入：事实 / 判断 / 反馈 / 已有方案 / 假设 / 冲突。
2. 形成问题陈述。
3. 梳理 As-Is 流程和关键断点。
4. 做根因分析；证据不足时标记待验证。
5. 定义目标、范围、非目标。
6. 识别业务对象、规则、角色和依赖。
7. 给出可验证的成功标准。
8. 输出可进入 `solution-design` 的分析结果。

## 输出

### 需求分析结果

- 背景与目标
- 目标用户与角色
- 核心场景
- As-Is 流程
- 核心问题陈述
- 根因分析
- 影响与优先级
- 核心业务对象
- 已知业务规则
- 本期范围
- 非目标
- 风险与依赖
- 验证指标
- 待验证假设
- 待决策事项

最后给出：`可进入方案设计 / 需回退澄清`。
