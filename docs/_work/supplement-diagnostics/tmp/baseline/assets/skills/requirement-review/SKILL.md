# Requirement Review

## 目标

独立判断需求材料是否足以进入研发和测试，优先发现会导致返工、线上风险或无法验收的问题。

## 前置条件

至少存在一份较完整的需求分析、方案或 PRD。只有模糊想法时，回到澄清/分析。

## 与 PRD Writing 的边界

- `prd-writing`：作者视角，负责把方案写清楚。
- `requirement-review`：审计视角，负责证明它是否站得住。

不得因为发现问题就悄悄改写规则；先指出问题和建议，由用户/业务确认后再修改原文。

## 评审顺序

1. 背景、目标与成功标准
2. 用户、角色与核心场景
3. 范围与非目标
4. 核心业务对象
5. 主流程与闭环
6. 状态流转
7. 权限与数据范围
8. 字段和数据口径
9. 异常与边界
10. 外部依赖与并发/失败处理
11. 页面与流程一致性
12. 验收标准与可测试性
13. 风险、迁移、兼容和上线条件

## 严重程度

- **S0 阻塞**：不解决无法可靠设计、开发、测试或验收。
- **S1 高风险**：可继续讨论，但直接开发大概率返工或产生线上风险。
- **S2 一般问题**：不阻塞，影响体验、运营、维护或文档一致性。
- **S3 优化建议**：当前方案可执行，但有更优选择。

## 每个问题必须包含

- 位置/对象。
- 问题是什么。
- 为什么是问题。
- 可能后果。
- 严重程度。
- 修改建议。
- 建议确认角色。
- 是否阻塞研发。

区分 `明确问题`、`优化建议`、`待决策事项`，不得把个人偏好包装成缺陷。

## 最终结论

- **GO**：无 S0，关键 S1 已处理或有明确可接受方案。
- **CONDITIONAL GO**：无 S0，但存在需在编码/上线前关闭的 S1 或明确条件。
- **NO-GO**：存在 S0，或关键规则/依赖无法确定预期行为。

## 输出

1. 总体结论：GO / CONDITIONAL GO / NO-GO
2. S0 阻塞项
3. S1 高风险项
4. S2 一般问题
5. S3 优化建议
6. 缺失规则与逻辑冲突
7. 待决策事项
8. 修改任务清单
9. 建议负责人角色
10. 下一步与复审条件
