# Solution Design

## 目标

建立 `需求分析 → 方案确认 → PRD` 之间的明确桥梁，避免在 PRD 阶段临时发明核心业务规则。

## 前置条件

应具备：

- 核心问题和目标用户。
- 关键场景与目标。
- 本期范围和硬约束。
- 已知风险、依赖和成功标准。

信息不足会改变方案方向时，回到 `requirement-analysis` 或 `requirement-clarification`。

## 核心职责

1. 明确设计目标和决策约束。
2. 对关键分歧形成 2–4 个候选方案。
3. 结构化比较并给出推荐方案。
4. 定义业务能力/模块边界。
5. 定义核心业务对象及关系。
6. 按实际范围定义端到端主流程，复杂业务可参考 3–6 条，不为数量虚构流程。
7. 定义关键状态及进入/退出条件。
8. 定义角色、数据范围和关键操作权限。
9. 定义页面/能力清单到足以进入 PRD 的粒度。
10. 标记技术评估项、业务待决策项和风险。

## 不负责

- 不写数据库 SQL、接口实现或部署方案。
- 不写完整字段级 PRD。
- 不替业务确认没有依据的规则。
- 不直接做最终研发放行评审。

## 方案对比规则

存在真实方案分歧时，至少比较：

- 对目标的覆盖程度。
- 实现复杂度。
- 业务风险。
- 技术风险。
- 对现有系统侵入性。
- 可扩展性与维护成本。
- 失败回滚成本。

必须给出一个推荐方案；允许保留次优备选，但不得并列第一。无法决策时明确指出缺失决策条件。

## 设计规则

- 模块是责任边界，不是页面或功能堆。
- 状态是一等业务概念；可被流程推动的核心对象必须有状态定义。
- 权限至少区分“可见”和“可操作”。
- 主流程只在此阶段建立骨架；详细异常由后续评审/Gate 扫描。
- 页面能力从业务任务反推，不从视觉布局反推业务规则。

## 输出

### 产品/业务方案设计

1. 设计目标与硬约束
2. 候选方案与对比矩阵
3. 推荐方案与放弃其他方案的原因
4. 业务能力/模块架构树
5. 模块职责与边界
6. 核心业务对象及关系
7. 关键状态与状态流转
8. 范围内核心端到端流程
9. 角色与权限框架
10. 页面/能力清单
11. 风险、依赖、技术评估项
12. 待业务决策事项
13. PRD 输入清单

最后给出：`方案可进入 PRD / 有条件进入 / 需回退分析`。
