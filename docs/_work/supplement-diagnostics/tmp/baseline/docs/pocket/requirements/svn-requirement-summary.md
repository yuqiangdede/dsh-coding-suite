# 交接文档 / 需求汇总（SVN 历史）功能约定

> 2026-11-05 变更：此入口现列入合并后的「文档」组，显示为「追溯需求」；分组及旧布局迁移以 [正式需求](project-handover.md) 顶部的已确认决定为准。下文原独立分组及按钮数量描述保留为历史背景。

状态：新增需求；2026-11-02。依据：用户提出「根据这个 svn 的提交记录，整理一下做的功能点」。扩展原[项目交接文档规格](project-handover.md)的五个按钮为六个，不更改既有五个按钮的身份、职责及已有权威规则。

## 目标与定位
「需求汇总」是从**指定 SVN 提交记录逆向归并完成的功能变更**，供交接、版本总结和知识梳理使用；不同于「功能规则」的当前版本行为核验，也不同于「验收文档」的正式需求编写。不得将提交说明直接推定为审批通过的原始需求、当前生效功能或上线结果。

## 按钮契约
- 组：`handover-docs`（交接文档），放在五个原有按钮之后；稳定 action ID：`handover-requirement-summary`，内置 Skill ID：`project-handover-requirement-summary`。
- 默认启用，不加入常用；默认组继续隐藏，不改变旧配置；已保存动作需显式补齐预设。
- 点击只插入可编辑的提示词草稿，不调用 SVN、不自动写文档、不自动发送；遵守初始化门禁、现有 Action schema v3、布局 v1 和权限策略。
- 支持粘贴日志、SVN XML/文本文件、可访问的 SVN 工作副本/明确 URL；分析用户提供内容不要求实时仓库连接。实时查询必须界定路径与修订/时间范围，默认只读。

## 处理规范
1. 明确来源路径、仓库、分支、版本范围和时区；仅用户已提供记录时覆盖其全部范围，范围不完整时标识，不补造。
2. 解析修订号、作者、日期、说明、变更路径；支持跨提交按业务模块归并并为每项列出全部修订号，处理重复、回滚、复制及合并。
3. 分类新增功能、功能调整、缺陷修复、性能/安全/稳定性、非功能变更；非功能项不得冒充功能点。
4. 产出简要统计、按模块去重功能清单、重点功能说明、非功能清单、修订号反向映射、待确认项及核验等级。
5. 有权限且材料可访问时核对 diff 和最新源码；无源码核验时清楚标「仅提交日志推断」。不可伪称测试通过或生产已上线。
6. 遵守项目初始化的 `docs/agents/document-layout.md`、既有权威目录和共享交接写入门禁。追溯工作稿统一使用 `<中间产物根目录>/requirement-trace/<任务ID>/requirements-from-svn.md`；同一任务复用、不同任务隔离，先预览内容或差异并取得明确确认。正式成果复用现有权威交接文档，写入前预览逐文件差异并等待明确批准；不得修改业务代码/仓库历史/生产或自动提交。

## 验收标准
- AT-SVN-01：新用户交接组出现第六按钮，五个旧 ID 与按钮次序保持不变。
- AT-SVN-02：旧保存按钮和分组布局不被覆盖，可通过「补齐缺失预设」新增；隐藏组和常用组保持原样。
- AT-SVN-03：内置 Skill 无外部下载依赖，Windows 离线插件包可加载；中英 UI 字段及默认表一致。
- AT-SVN-04：相同功能的多次提交归并成一个功能点且保留所有关联修订号。
- AT-SVN-05：混合一条业务变更、缺陷修复、纯格式化/构建提交时分类正确，统计可追溯。
- AT-SVN-06：回滚、分支不明、日志缺失、仅有标题等场景不会被认作当前已上线或完整覆盖。
- AT-SVN-07：提供日志文本即可完成分析，不强求 SVN CLI；没有输入且无权限时报告缺口，不能臆造历史。
- AT-SVN-08：追溯工作稿使用固定的 `requirement-trace/<任务ID>/requirements-from-svn.md` 相对路径；写入前按共享规程预览并确认。正式文档复用现有权威路径，不建立第二套知识库。
- AT-SVN-09：源码和发布 `lib/client.js` 的按钮表、组列表、接收指令一致。
- AT-SVN-10：不运行 SVN 修改命令、不执行生产连接、不泄漏凭据、不自动提交或推送。
