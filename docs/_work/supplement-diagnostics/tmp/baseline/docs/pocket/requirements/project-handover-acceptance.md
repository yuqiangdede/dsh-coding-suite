> 2026-11-05 变更：原独立分组相关用例由 [正式需求](project-handover.md) 顶部的合并决定取代。验收合并后唯一「文档」分组、现有按钮各出现一次、旧显隐按两个值的逻辑或迁移，以及自定义动作和常用顺序保留。其他适用的证据和写入保护用例继续有效；历史五按钮用例不代表当前实现。

状态：accepted acceptance criteria（2026-11-02；**需求和验收标准已确认，功能尚未实现/未执行测试**）。
依据：[正式需求规格](project-handover.md)；推荐实现细节：[技术实施方案](project-handover-implementation.md)。
设计核对代码基线：`master@a8b5d9d7f301cfe862162ae6dc93c00c28353d40`。测试时以具体实现分支和实际环境版本为准。
原则：**验收“有没有按要求实现”必须靠可复现的操作、产物和证据，而非提示词声称。**

## 1. 验收级别和发布门槛

- `P0`：可能造成旧配置丢失、用户文档被覆盖、敏感信息泄露、事实编造、未经授权写入/执行的阻断项。
- `P1`：核心流程、按钮、分组、证据、索引、增量维护、可读性或范围控制失效。
- `P2`：可用性、英文展示、扩展性和细节体验。
- **准入**：P0 全部通过；P1 全部通过或有明确批准且不影响核心目标的已记录豁免；P2 列出剩余问题和负责人。任何未执行案例标记 `NOT_RUN`，不能算 `PASS`。
- **产出**：用例 ID、版本/环境、步骤、期望、实际结果、日志/截图/文档路径、`PASS/FAIL/BLOCKED/NOT_RUN`、发现问题编号。测试无权限/无外网/无生产环境时不得将其替代为通过。
- 验收同时包括：静态/单元测试、发布 bundle 检查、真实 DSH UI 手工验证和至少两个目标项目演练（一个小项目、一个多模块项目）；不同验证维度不能互相替代。

## 3. 代表性验收测试夹具

建议准备可复现的**合成项目**，避免提交生产日志或真实用户数据：

1. `fixture-small-java`：Java 服务、2 个业务域、Controller/Service、配置、SQL 迁移、几个已有测试、日志配置；真实行为和资料版本均可核实。
2. `fixture-multi-module`：多模块 Java + Python 工具、异步消息/定时任务、跨模块调用、至少一个需分批分析的业务流程。
3. `fixture-doc-conflict`：已接受 ADR/需求与当前实现有意不一致，一项历史规范已经被继任文档替换，另一项无法判定环境适用性。
4. `fixture-layout-legacy`：`layoutJson` 旧版无新组字段、`documents` 显示=true、常用自定义顺序、禁用预设、自定义按钮及导入文件。
5. `fixture-manual-edit`：创建预览后由其他编辑器修改目标章节；验证确认写入前的二次比较。
6. `fixture-sensitive-logs`：使用**假的** Token、手机号、Cookie、相关 ID 和日志示例，检查最终 Markdown/JSON/输出摘要完全脱敏。
7. `fixture-no-runtime`：缺少运行环境/历史 Git/ Python/权限；应输出限制、降级策略，而非虚报成功。

夹具本身也必须含明确的项目基线和预期行为；不能让测试模型只依据文件名称猜规则。

## 4. 可执行测试方法（未来实现阶段）

### 4.1 静态与自动回归

在 Windows + Node 22 环境，根据实际 package scripts 运行：
- 单元层：布局解析/导入导出、五动作 ID/Skill ID、默认隐藏、补齐幂等/100 上限、本地化文案、旧 `handoff` 推荐隔离、用户保存配置保护。
- Skill 层：五个 `SKILL.md` frontmatter、资源相对引用、共用协议的缺失检测、离线资源加载。
- 项目样例层：同一事实索引、多批断点、待确认/冲突标注、来源指纹变化、无确认不写、并发冲突保护。
- 发布层：从实际源重建当前 Launcher bundle，再运行项目支持的 `build-action-bundle.mjs --check`、`verify-client-bundle.mjs`、`verify-launcher-render.mjs` 和相应 Node 测试；每条命令记录原样退出码和失败原因。

脚本名称为当前仓库已存在的检查入口，并不表示本 PR 已运行这些测试。未来实际运行前应查看最新脚本与依赖，不能为了文档功能删减已有相关测试。

### 4.2 人工 UI 验收

- 在真实 DSH Windows 桌面宿主进行中文、英文、窗口宽度变化、键盘访问、显隐/保存/重启、禁用及只读状态检查；
- 校验按钮插入的文本可编辑、发送前没有执行动作；保存版本冲突应明确提示而非覆盖；
- 对比旧版本导出 JSON 与升级后再导出的配置，逐字段核对用户数据；
- 明确记录真实宿主 UI 测试与 `stub-render`、单元测试的区别。

### 4.3 人工交接可用性验收

由**未参与整理**的接手人员仅凭生成资料完成下列任务，并记录是否查得到来源：
- 说明某业务模块的用途、适用角色和关键例外条件；
- 顺着某条关键流程找到入口、状态变更、外部接口/持久化节点；
- 根据模拟故障现象找到日志线索、代码出口和下一步只读验证方法；
- 说出当前分析版本、哪些内容缺乏运行验证、哪些模块仍未覆盖。

这部分可用性验收优先于“生成了几份文档”或“文本字数”之类的形式指标。

## 6. 本轮状态与后续实施门槛

本轮的交付物**只有 Markdown 需求与设计/验收文档**。不增加按钮、不安装 Skill、不修改程序、不运行目标项目或生产环境，也不声称 AT 项已通过。

未来实施建议采用四阶段：①分组与保存兼容；②入口、证据和文档；③差异预览与人工保护；④多模块、离线及真实宿主验收。每阶段产物和回归结果应链接到本规范；阻断问题未解决不得宣布整体可验收。
