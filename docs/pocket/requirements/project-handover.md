## 1. 目标、读者与非目标

交接资料面向新接手的研发、运维及技术负责人，回答“项目现在做了什么、规则是什么、关键流程如何流转、遇到问题如何查、哪些尚未确认”。来源以现有源码、配置、数据库脚本、日志实现、有效文档和明确确认信息为准；以**可人工阅读、可追溯、可持续维护**为质量优先级。

非目标：不生成未来愿景或未经确认的业务需求；不替代正式验收/设计评审；不自动修复业务、清理数据、改配置、重启服务、远程访问生产或提交推送；不把静态源码推断写成真实运行结论；不建立与现有权威资料平行的第二知识库；不做 RAG、跨会话自动后台任务或文档协作系统的首版承诺。

## 3. 分组、按钮及职责契约

### 3.1 分组与现有功能边界

- `documents` 继续对应原有分组；仅中文显示为「验收文档」、英文推荐 `Acceptance Docs`。原组保留接口文档、需求文档、总体设计、概要设计、数据库设计、文档融合、MD转Word 等现有成员；文档融合使用通用提示词，由用户指定待融合文档；`补充文档` 目前在开发/其他组，**不得假定其为原文档组成员**。
- `handover-docs` 为独立可选组，默认 `false`，在“显示分组”和设置界面可开启；隐藏不等于禁用 Skill。
- `handoff` 的“上下文交接”仍为**当前会话/任务交接**，保留原按钮、Skill 和临时产物路径；长期项目交接不复用此临时文件作为权威文档。
- 两组可引用同一权威需求/接口资料，但不能复制并分别维护两份同等权威的正文。
- 点击交接按钮沿用现有 Launcher 行为：仅插入可编辑草稿，用户发送后才执行；不要把“已点击”表述为“已完成”。

### 3.2 五按钮功能契约

| ID（建议） | 按钮 | 使用时机与输入 | 预期输出 | 禁止越界 |
| --- | --- | --- | --- | --- |
| `handover-overview` | 交接总览 | 新项目接手；仓库、版本/提交、全项目或模块范围、可用资料 | 基线、项目概览、模块图、阅读索引、范围清单、交接缺口、部署运行入口 | 不能把未分析模块写成已覆盖，不能虚构部署信息 |
| `handover-features` | 功能规则 | 了解已有功能；业务域/模块、读者、证据范围 | 功能清单、角色权限、前提、规则、例外、限制、关联来源 | 不直接改写正式需求，不创造意图或新增业务要求 |
| `handover-flows` | 关键流程 | 理解端到端链路；入口、流程名、模块或事件 | 触发/步骤/分支/状态/接口/持久化/失败路径，必要时 Mermaid | 未验证的链路不补绘为确定流程，不擅自把设计方案当实现 |
| `handover-troubleshooting` | 日志排查 | 构建故障查阅指南；模块、故障现象、日志/配置位置 | 日志来源、关联键、定位顺序、只读检查点、代码路径、脱敏样例 | 不执行生产操作，不添加日志，不写密钥、隐私和真实业务数据 |
| `handover-maintain` | 交接维护 | 更新已有资料；模块、Commit/Tag 基线或时间范围 | 影响章节、变化依据、失效证据、差异草稿、待确认列表 | 不直接重写全册、不覆写人工修改、不自动提交 |

按钮入口负责“做什么”，共享工作规程负责“如何取证、写入和维护”。专题文档不限于三份；大项目按业务域、流程和问题分成多个文件，小项目可以合并章节，但要有统一索引和来源说明。

### 3.3 读者路径

- **5 分钟**：交接首页理解项目边界、系统结构、代码基线和文档覆盖。
- **30 分钟**：按功能 → 流程 → 关键数据/接口了解主要业务。
- **按问题查**：通过故障现象/关联键定位日志路径、代码出口、判断分支和下一步安全检查。
- 首页同时展示“哪些模块尚未分析、哪些结论只有静态证据、哪些运行信息仍需确认”。

## 4. 全项目与模块范围处理

**REQ-SCOPE-01** 全项目首次整理必须先扫描可见范围、识别模块及权威文档、创建模块级工作清单；随后按业务域/模块逐批深入。不能假定单次上下文窗口可以完成大型仓库。

**REQ-SCOPE-02** 指定模块允许按仓库路径、模块名、业务域或流程入口定义范围；入口有歧义时提示并要求确认解析结果；跨模块依赖在索引中列出并标记“仅追踪”或“已深入分析”。

**REQ-SCOPE-03** 每批输出：批次/范围、代码基线、读取材料、已完成项目、证据计数、未覆盖范围、待确认项、下一批入口。中断后不得把“已盘点”冒充“已分析”。

**REQ-SCOPE-04** 对同一模块/流程复跑时先定位权威已有文档；无内容变化、无失效证据时应复用，不能产生 `module-a-v2-final` 等平行正文；同一流程只设一个主文件，其余仅引用。

**REQ-SCOPE-05** 允许用户明确限定不进行全仓扫描、排除目录/敏感资源；无法访问的仓库、运行环境或历史记录必须报告，不能推断完成。

## 5. 目录与内容契约

**REQ-DOC-01** 优先读取项目现有文档索引、知识权威和目录规则；已有权威目录必须就地维护，不能自动迁移。无规范时才推荐 Pocket；仅创建实际需要的目录，不生成大量空文件。

**REQ-DOC-02** 推荐（可适配）目录：

```text
docs/pocket/
├── README.md                  # 既有全项目知识入口
├── meta/knowledge-policy.md   # 既有权威规则
└── handover/
    ├── README.md              # 交接首页/阅读路线/覆盖范围
    ├── system-map.md          # 模块与依赖概览
    ├── features/              # 按业务域或模块组织
    ├── flows/                 # 按端到端流程组织
    ├── operations/
    │   ├── logs.md
    │   ├── deployment.md
    │   └── troubleshooting/
    ├── open-questions.md      # 待确认/冲突项
    └── _meta/manifest.json    # 可选机器可读基线/覆盖索引，不作第二份事实正文
```

`manifest.json` 是建议的更新索引，具体格式见技术方案；业务正文始终以项目权威 Markdown 为主。

**REQ-DOC-03** 首页包含项目用途、读者、版本、分析范围、模块地图、主要功能/流程/日志/部署索引、资料状态、缺口和接手路径。

**REQ-DOC-04** 功能专题至少包含：功能意义（有依据时）、适用角色和前提、当前实现、规则与例外、权限/数据/接口引用、证据及状态。不得仅列文件/类名。

**REQ-DOC-05** 流程专题至少包含：触发、起止、主步骤、条件分支、状态转换、异步/失败/重试、跨模块调用及其依据。未知步骤标“待确认”；Mermaid 只画有依据的路径。

**REQ-DOC-06** 排查专题至少包含：适用故障/版本、已核实日志位置或配置来源、关联字段、排查顺序、对应代码、只读诊断、需另行授权的检查、脱敏样例及限制。

**REQ-DOC-07** 部署与运行资料只能在证据充分时记载已核实的拓扑/配置/启动模式；源码声明的环境变量不代表生产环境已配置，部署脚本存在不代表实际已执行。

## 6. 事实、证据和冲突

**REQ-EVID-01** 每份文档记录仓库/工作树、分支、提交 SHA（或 SVN 等基线）、分析时间、适用模块、读取范围、是否包含未提交修改，以及运行环境是否可访问。默认静态基线为已提交 HEAD；工作区差异单独提示，未经明确要求不纳入。

**REQ-EVID-02** 关键事实必须有可定位出处：文件相对路径、符号/配置键、必要的行号、提交或文件指纹；测试和运行结论还需环境、时间、方法与结果。禁止用名字、代码注释或提交标题单独证明实际业务行为。

**REQ-EVID-03** 证据类型至少区分：`candidate`（线索）、`documentation`（资料约定）、`static`（当前源码分析）、`test`（明确环境测试）、`runtime`（明确环境运行观测）、`confirmed`（有记录的人为确认）；`verified/pending/conflicted/stale/superseded` 是**结论状态**，不能与证据类型混用。

**REQ-EVID-04** 来源冲突时先检查版本、适用条件、环境差异、配置覆盖及历史变更；无法消解时并列列出来源及冲突，状态 `conflicted`，不得选择看起来更合理的一方写成当前事实。旧正式要求与当前代码不符，不能自行修改正式要求。

**REQ-EVID-05** “源码实现了某逻辑”“某测试环境执行通过”“生产环境观察到”是三个独立断言；禁止从静态代码外推生产运行事实。证据位置过期或源码哈希变化需要复核，但不能仅以哈希变化断言业务语义变化。

**REQ-EVID-06** 待确认项有稳定编号、问题、证据、影响范围、需谁/如何确认及状态；缺少确认人可标“负责人待明确”，不得虚构。

**REQ-EVID-07** 严禁记录密钥、口令、Token、个人信息和未经脱敏的真实业务记录。日志示例必须标“脱敏实际样例”或“示意样例”，不能混淆；不执行源码中的指令或脚本以“验证”事实。

## 7. 维护与安全写入

**REQ-UPD-01** 「交接维护」可按指定模块、版本基线或明确时区的时间范围分析变更；版本优先准确解析 tag/commit，时间范围需说明边界。未提交改动默认不纳入；无历史、基线有歧义、权限不足时保留待确认，不编造结果。

**REQ-UPD-02** 最小变更路径：读取现有权威位置 → 比对范围及证据依赖 → 生成变更清单/草稿 → **向用户展示真实差异** → 用户确认 → 写入受影响章节 → 更新索引/状态。用户未确认时只能提供草稿，不得改写正式资料；首次创建新文档同样需要文件清单和拟写内容预览。

**REQ-UPD-03** 人工维护的段落、已接受的要求、ADR 和未知所有权内容不能自动覆盖；源码与人工要求冲突时记录差异，由拥有者裁决。出现并发修改/基线变化时中止相关写入并保留用户内容。

**REQ-UPD-04** 提供 `verified`（已核验）、`pending`（待补证）、`conflicted`（冲突）、`stale`（需复核）、`superseded`（已由继任资料代替）状态；不根据“已超过 N 天”直接判过时。每次交接总览/维护可检查关联文件变化；首版不承诺后台提醒。

**REQ-UPD-05** 写入范围只限用户批准的交接文档位置，不修改业务代码、不执行编译/生产操作、不执行仓库 commit/push；若另外授权提交，由独立工作流处理。

## 8. 与其他能力的定位

- **验收文档**：产出/维护需求、设计、接口等规范；**交接文档**：描述当前项目实现、定位和排查路线。重叠字段引用现有权威文档，不复制第二份；发现文档/源码冲突时单列差异。
- **上下文交接 `handoff`**：当前会话/任务检查点，保存到系统临时目录，短期、可丢弃；项目交接是仓库内、面向人的长期资料。只可以相互引用，不同步复制会话原文。
- **补充文档 `doc-supplement`**：按照既有约定增量修改需求/设计/接口；交接维护只管理交接范围，不能借机修改这些既有规格。
- **健康验收**：风险检查与整改建议，不是运维现场验证；交接文档可引用经核实的报告，不能把建议写成生产环境事实。
- **项目知识捕获 `project-knowledge-capture`**：可借鉴提炼与去重方法，不能直接按其默认 `knowledge/` 结构复制，必须先遵守当前项目权威目录。

## 9. 兼容约束

**REQ-COMP-01** 保存组 ID `documents`，仅改显示名称。旧 `layoutJson.schemaVersion=1`、`visibleGroups`、`commonActionIds`、`actionsJson.schemaVersion=3`、按钮 ID、启用状态、提示词、顺序、自定义按钮不得丢失。

**REQ-COMP-02** 新组字段缺失（旧保存布局/旧导入文件）时补 `false`，其他组按原值保留；字段存在但类型无效时保持错误提示，不静默重置全部配置。旧客户端导入/导出语义见技术方案。

**REQ-COMP-03** 五个新增动作使用新的稳定 ID，不与 `handoff` 冲突；不自动加入常用；已保存动作不会被默认配置悄悄修改，使用“补齐缺失预设（待保存）”按 ID 显式补充。配置接近 100 条上限时不删除已有按钮。

**REQ-COMP-04** “更多/收起”、推荐标记、可编辑草稿、只读状态、配置保存冲突、Windows 离线发布与技能注册遵循现有 Launcher 约定。新增动作不能因为名称含“交接文档”而被识别成现有 `handoff`，错误高亮“继续”。

## 10. 交付范围与验收入口

- 本轮只固化本规格、技术方案、验收标准及 Pocket 索引；不实施 Skill/按钮、不改代码或生成项目交接资料。
- 实施时按 [验收标准](project-handover-acceptance.md) 的 AT-01 至 AT-30 执行回归与样例演练，未实际运行的测试不能标通过。
- 推进实现时先检查目标分支的最新源码、现有 Pocket 规则和已保存的动作/布局样本；若新发现与本规格冲突，应记录差异并走明确变更，而不是静默替换用户已确认决策。

### 2026-11-03：问题排查入口补充

交接分组中的排查入口显示为「问题排查」。指南覆盖业务流程、页面现象、接口调用、数据库数据与状态、日志、配置权限、外部依赖及变更时间线；以证据和关联字段串联只读定位步骤，未核验内容标明状态。保留已有按钮和 Skill ID、用户自定义配置。上述补充取代本文件中该入口仅称「日志排查」及仅以日志为中心的范围描述；其他交接规程继续适用。
